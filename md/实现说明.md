# 四题实现说明

四道题的入口分别为 `1.md`、`2.md`、`3.md`、`4.md`。实现直接接入数据库内核；文件解析没有使用外部 SQL 引擎，模型测试不需要真实模型凭据。

## 1. AI 函数

- `AI_PROMPT` 保留 JSON 和 TEXT/LOB 类型，递归展开嵌套 Prompt，逐次替换重复占位符并检查下标溢出。替换后的参数内容不会再次作为模板解析。
- Completion 使用 JSON 对象配置，支持 NULL 配置和长文本，并拒绝空或类型错误的响应。`system_prompt` 配置映射到 Provider 的系统提示，不作为普通请求选项传给 Provider。
- Embedding 校验返回数量、下标唯一性、维度和有限数值；OpenAI 的乱序结果按 `index` 恢复。批执行把最多 64 个有效输入按模型和维度分组，单独维护原始行号，跳过过滤行和 NULL 输入。
- Ollama 的 Provider 名称忽略大小写，允许空 Key，使用原生非流式生成和 Embedding 协议。
- Rerank 校验完整的下标集合、数量和分数，对每批结果加全局偏移，再按分数降序、原始下标升序合并；对象输入保留原始字段。
- HTTP 接收限制为 64 MiB，并处理重试缓冲区和失败分配的释放。AI 列的持久重试预算覆盖传输重试，避免嵌套重试放大模型调用次数。

## 2. 文件 SQL

SQL 解析器和 Resolver 生成动态列，执行器复用原生关系运算。CSV、JSONL、Parquet 的解码通过既有 CXX 集成调用 Rust 模块；WHERE、JOIN、聚合、排序和 LIMIT 由 seekdb 执行。

`enable_file_sql` 默认关闭。启用后仍检查 `secure_file_priv`，并限制为普通本地文件。Linux 上以目录句柄和 `openat/O_NOFOLLOW` 固定实际访问路径，检查文件身份和修改时间。Schema 推断完整扫描文件，但不保留全文件数据；执行阶段支持列裁剪、批次读取和重扫。单记录及批次有内存边界。

CSV 支持表头、重复列名、UTF-8、引号、转义和字段内换行。字段内的 CRLF 原样保留。JSONL 合并字段并为缺失字段补 NULL，拒绝重复字段及嵌套结构。Parquet 使用 Footer Schema 并支持多 Row Group 和 Snappy。

`COPY` 先写临时文件，查询成功后发布；目标存在则失败。错误和对象销毁都会清理未发布文件。文件路径和读取选项不参与普通常量参数化，避免不同文件错误复用动态列定义。

## 3. 异步 AI 列

Schema 保存原始表达式、规范表达式、依赖 ID、定义版本、重试配置及三个隐藏列的 ID。类型要求作为系统提示加入 Completion 配置，原始模型输入保持独立。业务 SQL 不能直接写入结果列。

隐藏状态是持久任务的存储：结果失效、请求标识变化和 PENDING 状态随业务行在同一事务写入。后台只能读到已提交的任务；回滚恢复原状态，删除业务行同时删除待办。普通列更新只有命中依赖或主键时才使结果失效。同一行同次变更的 AI 列共享请求标识。

后台服务在模型请求前持久化次数，成功或最终失败的单列结果先保存到隐藏结果描述中。所有相关列达到终态后，使用一条原生 UPDATE 原子发布结果和 READY/FAILED 状态。发布同时比较主键、请求标识及表定义版本。已保存的兄弟列结果可在中断后复用。

`oceanbase.__all_ai_column_task` 是管理员只读任务视图，直接展开当前持久状态，能看到本事务内的任务创建、回滚和删除。它提供表/列 ID、请求分组、主键条件、可执行时间、阶段及重试次数。

`ALTER TABLE ... RETRY AI COLUMN ... WHERE ...` 走事务性 UPDATE。未加反引号的 `status` 表示 AI 状态，带反引号的表示业务列。`ai_column_strict_read` 在执行前检查计划引用的 AI 列，对整列存在的未就绪行返回错误 11120；普通列不受影响。向量失效和发布均经过原生 DML 的索引维护路径。

后台使用四个工作线程，按表 ID 固定分配任务所有权。同一张表由一个线程处理，避免重复领取；不同表可以并发调用模型。没有引入跨进程任务租约，同一表内的行仍串行处理。

## 4. 全文索引

IK 字符分类只解码一次 Unicode，再按原有顺序判断分类，减少多次重复解码。BENG 为 UTF-8 ASCII 词元增加直接小写化路径；已全小写的词元复用原缓冲区，其他字符和编码仍走原有字符集转换。

进一步将 IK 词典分段按起始字符排序，查询时二分定位最后一个起点不大于目标字符的分段，再检查包含式上界。字符比较仍使用原有 UTF-8 二进制排序规则；空词典及分段之间的间隙仍返回未命中。每次字符定位的比较次数由 O(R) 降为 O(log R)。

Unicode 分类边界、可用的 UTF-16 编码以及英文转换回归已通过。新增词典分段优化的 C++ 编译已完成，但最终链接和新边界测试被 WSL 文件系统只读故障中断，仍需完成验证。已有完整基准没有证实稳定的整体收益，不能声明第四题已通过性能验收。原始数据和限制见 [全文性能报告](全文性能报告.md)。

## 验证入口

在准备好 Linux 工具链后，从仓库根目录执行：

```bash
cargo test --offline --manifest-path rust/Cargo.toml -p file-scan

python3 build.py test \
  //unittest/sql/engine/expr:test_ai_prompt \
  //unittest/sql/engine/expr:test_ob_openai_utils \
  //unittest/sql/parser:test_file_sql_parser \
  //unittest/sql/parser:test_ai_column_parser \
  //unittest/sql/resolver:test_ai_column_resolver \
  //unittest/share:test_ai_column_schema \
  //unittest/share:test_text_analysis \
  //unittest/storage/fts:test_fts_hotpaths \
  --test_output=errors
```

如果运行环境没有系统安装的 libaio 等依赖，给测试设置 `--test_env=LD_LIBRARY_PATH=$PWD/deps/3rd/usr/local/oceanbase/deps/devel/lib`。

SQL 端到端测试使用专用本地实例：

```bash
export MYSQL='deps/3rd/u01/obclient/bin/obclient -h127.0.0.1 -P2887 -uroot'
python3 -m unittest discover -s unittest/sql/engine/expr -p 'test_ai_functions.py' -v
python3 -m unittest discover -s unittest/sql/engine/expr -p 'test_ai_columns.py' -v

# FILE_SQL_ROOT 须位于实例的 secure_file_priv 允许目录内。
export FILE_SQL_ROOT=/absolute/allowed/test-directory
python3 -m unittest discover -s unittest/sql/engine/basic -p 'test_file_sql.py' -v
```

仓库配套 mysqltest 位于 `ai_function`、`file_sql`、`ai_column` 三个 suite。全文性能测试使用 `tools/benchmark/fts_large_bench.sh` 和现有评分脚本；保持题目规定的数据、参数和基线不变。
